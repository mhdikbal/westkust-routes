# Production Research Page — SEC-3 Account Provisioning Runbook

> **Procedure document. No real account, username, password, or hash was created by this document.**
> **No actual usernames are specified anywhere below.**

---

## 1. Preconditions

- `SEC-DEC-11` (credential-store topology) approved — see `PRODUCTION_RESEARCH_PAGE_SEC3_CREDENTIAL_STORE_DESIGN.md`.
- A researcher-approved pilot-user list exists, naming individuals and roles (not produced by this runbook — this is item 4 in the remaining-decisions list).
- A secure credential delivery channel is agreed (item 5 in the remaining-decisions list) — e.g. a password manager share, not email or chat.
- Maintenance window approved (item 7).

## 2. Provisioning Steps (procedure, not executed)

1. **Researcher-approved username.** For each pilot user, obtain their approved account name from the pilot-user list. Format convention only (illustrative, not a real value): `firstname.lastname` or an institutional identifier — decided by the researcher, not generated by this procedure.
2. **Assigned role.** Record alongside the username in the provisioning log (not the credential file itself, which has no role field) — e.g. "researcher, read access to `/riset/pemodelan/` and `/linimasa/` only" if per-route scoping is later desired (out of scope for the Basic Auth transition, which is all-or-nothing per credential; a future OIDC migration could add per-route authorization).
3. **Secure password generation or entry.** Two acceptable methods:
   - Generate with a cryptographically secure random generator (e.g. `openssl rand -base64 24`, run in a shell that does not log to persistent history — `HISTCONTROL=ignorespace` prefixed with a space, or a non-interactive script) and deliver via the approved secure channel (item 5) without ever displaying it in a terminal that is screen-shared, recorded, or logged.
   - Let the pilot user choose their own password via a secure, one-time-use delivery mechanism (e.g. a self-destructing secret link) that the provisioner never sees.
4. **No password in shell history.** Any interactive step must use a method that does not persist the plaintext to `.bash_history`/`.zsh_history` (a leading space with `HISTCONTROL=ignorespace`, `set +o history` bracketing, or a script that reads from a pipe/file descriptor never echoed to the terminal).
5. **No password in terminal report.** No provisioning script's stdout, and no chat/report summarizing this runbook's execution, may include the plaintext password, its hash, or any Authorization header value — consistent with every prior SEC-2/SEC-2A/SEC-3 output.
6. **Password hash creation.** `htpasswd -B` (bcrypt, matching the hash format already used in every SEC-2/SEC-2A prototype) against a **new** file, never the live credential store directly.
7. **Atomic htpasswd update.** Per `PRODUCTION_RESEARCH_PAGE_SEC3_CREDENTIAL_STORE_DESIGN.md` § 4 — build the new file, verify it, then atomically replace the live path.
8. **Account disablement.** Remove the user's line from the htpasswd file (or comment convention is not supported by the htpasswd format — removal is the only mechanism) and atomically replace, same as rotation.
9. **Password rotation.** Same atomic-replace procedure as initial provisioning, on the existing username's line.
10. **Account revocation.** Same as disablement — immediate, atomic, no grace period unless the researcher explicitly requests a transition window.
11. **Credential delivery through a separate secure channel.** The channel used to notify the pilot user that provisioning is complete (e.g. a calendar invite, an in-person handoff) must be **different** from the channel used to deliver the password itself (item 3), so a single compromised channel cannot yield both "who has an account" and "what the password is."
12. **Audit record.** Each provisioning/rotation/revocation event is logged with: timestamp, username, action (create/rotate/disable/revoke), and the operator who performed it — **never** the password or hash value itself.
13. **Day-45 review.** Per `SEC-DEC-07`, a checkpoint before the 60-day expiry — confirms which accounts are still needed, flags any that should be revoked early, and begins planning the Entra/OIDC migration (`SEC-DEC-06`) if not already underway.
14. **Day-60 expiry.** Per `SEC-DEC-07`, no automatic extension — expiry requires an explicit new researcher decision to renew, extend, or complete the migration to Option B (Entra/OIDC).

## 3. What This Runbook Does Not Do

- It does not name any real person, username, or role.
- It does not generate, store, print, or transmit any real password or hash.
- It does not create `htpasswd` file content of any kind, real or dummy, in the repository.
- Executing this runbook against production remains gated behind: `SEC-DEC-11` approval, the pilot-user list, the secure delivery channel decision, and the maintenance window — all listed as remaining decisions in `PRODUCTION_RESEARCH_PAGE_SEC3_PRODUCTION_LIKE_PLAN.md` § 9.
