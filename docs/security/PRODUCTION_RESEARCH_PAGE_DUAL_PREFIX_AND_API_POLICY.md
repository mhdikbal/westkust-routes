## PHASE 2: DUAL-PREFIX POLICY

### 2.1 Canonical Policy

```text
P1 — protect both /atlas/ and /westkust/ identically, applied first.
P2 — evaluated afterward: redirect one prefix to the canonical prefix.
P3 — not adopted (retiring a prefix is a separately approved compatibility
     decision, out of scope for this transitional design).
```

This matches the researcher's own direction ("P1 first, then evaluate P2") and the plan's instruction not to leave one prefix unprotected.

### 2.2 Exact Protected Location Blocks (design, not applied)

Both existing blocks in `silida.conf` — `location /atlas/` and `location /westkust/` — proxy to the identical upstream (`http://127.0.0.1:8084/`) and already share nearly identical directives (`proxy_redirect`, `sub_filter`, cache-control overrides). The containment design adds an authentication directive **to both blocks identically**, whichever mechanism is chosen (Option C: `auth_basic`+`auth_basic_user_file`; Option B: `auth_request` pointed at the identity-aware proxy, or the proxy sitting in front of both blocks).

Because the three candidate pages (`/riset/pemodelan/`, `/riset/pemodelan/panduan/`, `/linimasa/`) are a *subset* of everything reachable under `/atlas/`/`/westkust/` (which also includes the public root `/`, `/ports/<slug>/`, and the four out-of-scope thesis-only pages `/riset/tema/`, `/riset/petunjuk-arsip/`, `/riset/jaringan/`, `/riset/atjeh-dagang/`), the design requires **nested, path-specific location blocks** inside each prefix, not a blanket lock on the whole `/atlas/`/`/westkust/` prefix:

```text
location /atlas/riset/pemodelan/     { <auth directive>; proxy_pass ...; }
location /atlas/linimasa/            { <auth directive>; proxy_pass ...; }
location /westkust/riset/pemodelan/  { <auth directive>; proxy_pass ...; }
location /westkust/linimasa/         { <auth directive>; proxy_pass ...; }
```

(`/riset/pemodelan/panduan/` is a child of `/riset/pemodelan/` and is covered by the same prefix match, provided nginx's longest-prefix-match precedence is respected — see §2.3.)

### 2.3 Precedence and Regex Risks

- Nginx resolves location blocks by **longest matching prefix** among non-regex (`location /path/`) blocks, unless a regex (`location ~`) block matches, which takes precedence regardless of length. **Neither existing `/atlas/` nor `/westkust/` block uses regex matching** (confirmed by reading the live config) — so a new plain-prefix child block (`/atlas/riset/pemodelan/`) will correctly take precedence over the broader parent (`/atlas/`) without needing regex, avoiding the most common nginx precedence pitfall.
- **Risk to design around:** `/riset/pemodelan/` as a prefix will also match `/riset/pemodelan/panduan/` (desired — panduan should inherit protection) but nginx prefix matching is *character*-based, not path-segment-based — a hypothetical future route like `/riset/pemodelanX/` would also match the `/riset/pemodelan` prefix if the trailing slash were omitted from the location pattern. **Design requirement:** always write the child location with the trailing slash (`location /atlas/riset/pemodelan/ { ... }`), exactly matching the existing pattern already used throughout `silida.conf`, to avoid this class of accidental over-match.
- **Risk:** the existing `sub_filter` rewriting (`href="/` → `href="/atlas/`) operates on response *bodies*. If an auth challenge or login-redirect response is generated by an identity-aware proxy sitting in front of these blocks (Option B) rather than by the Django app itself, that response will **not** pass through the existing `sub_filter`/`proxy_redirect` directives unless the new block explicitly includes them — a design detail to carry into the Option B target plan (see the Entra/OIDC document, §"Handling of /westkust/").

### 2.4 Trailing-Slash Behavior

Unaffected by adding auth — Django's `APPEND_SLASH` redirect behavior (`/atlas/linimasa` → `Location: /linimasa/`, rewritten by the existing `proxy_redirect / /atlas/;` to `/atlas/linimasa/`) occurs **after** nginx has already matched the request to a location block and (for Option C) already required Basic Auth credentials before proxying — meaning the auth challenge fires on both the slash and no-slash variant, since both match the same new child location block by prefix. No additional design needed here beyond what's already tested implicitly by the existing prefix-matching behavior.

### 2.5 `proxy_redirect` Behavior

The new child blocks must **repeat** the existing `proxy_redirect / /atlas/;` (or `/westkust/` equivalent) directive — `proxy_redirect` is not inherited automatically from a parent `location` block in nginx once a more specific child block is matched for the request; each block that proxies must declare its own. This is a concrete implementation requirement to carry into whichever option's actual config change is eventually authorized (not performed this turn).

### 2.6 Direct Child Routes

`/riset/pemodelan/panduan/` is the only true child route among the three candidates and is covered by §2.2's prefix design. No other child routes exist under `/linimasa/` (verified against the full `urlpatterns` list in the prior SEC-0 route inventory — `/linimasa/` has no sub-paths).

### 2.7 Redirects After Login

For Option C (Basic Auth), there is no "login redirect" — the browser re-sends credentials automatically per-request once cached; no redirect design is needed.

For Option B (OIDC), the redirect-after-login must restore the **original prefix** (`/atlas/...` or `/westkust/...`) the user requested — this is a direct consequence of §2.1's "protect both identically" policy: whichever prefix initiated the auth flow must be the one the user lands back on, not a hardcoded canonical prefix (until/unless P2 is later adopted). Detailed in the Entra/OIDC target design document.

### 2.8 Public Routes That Remain Unaffected

`/`, `/ports/<slug:slug>/`, `/riset/tema/`, `/riset/petunjuk-arsip/`, `/riset/jaringan/`, `/riset/atjeh-dagang/`, `/riset/enclave-1682/`, `/api/health`, `/api/forts/*`, `/api/voyages/*`, `/api/glossary/*`, `/docs`, `/openapi.json` — none of these are inside the new nested child location blocks defined in §2.2, and the parent `/atlas/`/`/westkust/` blocks continue to serve them exactly as today, unauthenticated. Confirmed by design (the new blocks are narrower, additive siblings, not replacements of the parent blocks).

## PHASE 3: API PROTECTION POLICY

### 3.1 Shared-Consumer Audit (performed this turn, read-only)

Searched the entire `frontend/` tree (`*.html`, `*.js`, `*.py`) and the relevant `backend/` modules for any reference to `research/linimasa` or `research/pemodelan-dashboard` outside the three candidate views:

```text
grep -rl "research/linimasa|research/pemodelan-dashboard" frontend/ →
  frontend/map_app/views.py                          (the 3 candidate views themselves)
  frontend/map_app/tests.py                           (unit tests for those views)
  frontend/map_app/templates/map_app/riset_pemodelan.html
  frontend/map_app/templates/map_app/riset_pemodelan_panduan.html
  frontend/map_app/templates/map_app/linimasa.html
```

**Result: no other page, template, or script consumes either endpoint.** `backend/models.py`, `backend/build_bokeh_dashboard.py`, `backend/seed_linimasa_events.py` reference the underlying data models/build scripts, not the HTTP endpoints, and are not public-facing consumers.

### 3.2 Classification (per plan §3.3 vocabulary)

```text
GET /api/research/linimasa            → AUTHENTICATED_RESEARCH_API
GET /api/research/pemodelan-dashboard  → AUTHENTICATED_RESEARCH_API
```

**No public/private response split is required** — both endpoints are exclusively consumed by the three pages this plan already intends to protect. This satisfies the plan's own conditional instruction ("If only protected pages consume an API: classify it AUTHENTICATED_RESEARCH_API; require the same identity boundary as the HTML pages") without needing the more complex "public/private split" branch.

### 3.3 Backward Compatibility

No external consumer exists to break — confirmed by §3.1. No API contract change (response shape, field set) is proposed; only an authentication *boundary* is added in front of the existing endpoints. The existing `/docs`/`/openapi.json` schema exposure (noted in SEC-0 discovery as a minor finding — these disclose the *shape*, not content, of the two endpoints) is unaffected by this design and remains a separate, lower-priority item.

### 3.4 Design: How the API Boundary Is Enforced

Both candidate APIs sit under the direct, prefix-agnostic `location /api/` block in `silida.conf` (not under `/atlas/`/`/westkust/` at all — confirmed in SEC-0 discovery). Two design-consistent approaches, to be finalized once SEC-DEC-02 (N1 vs N2) and the Option B/C selection are made:

- **Path-specific carve-out inside `/api/`:** add narrower `location /api/research/linimasa` and `location /api/research/pemodelan-dashboard` blocks (again exploiting nginx's longest-prefix-match precedence, §2.3) with the same auth directive as the HTML pages — leaves the rest of `/api/` (forts, voyages, glossary, health, and the four out-of-scope research endpoints) untouched.
- **Application-layer guard (Option A/B only):** a FastAPI `Depends(...)` on just these two route functions, checking a session/token issued by the same identity boundary as the Django pages — this is the only approach that also survives the F-03 direct-backend-port bypass (see network containment plan §4) without relying on nginx-layer enforcement at all, and is the stronger design for Option B specifically.

### 3.5 Direct-IP and Alternate-Host Behavior

Until SEC-DEC-02 (network containment) is approved and applied, **both candidate APIs remain reachable unauthenticated via `http://<VPS-IP>:8084/api/research/linimasa` and `.../pemodelan-dashboard`**, regardless of whatever auth is added at the `silida.org` nginx layer — this is the same F-03 finding, restated for the API surface specifically. **API protection (this document) and network containment (the companion plan) are not independent — API protection alone is insufficient without network containment, and vice versa.** This dependency is carried into SEC-DEC-04's evidence trail.
